# Sportzal Data Contracts v1

## Назначение и канон

Два внешних документа: `sportzal.program` (ИИ → приложение) и `sportzal.ai_snapshot` (приложение → ИИ). Канон — этот документ, [program.schema.json](schemas/program.schema.json), [ai-snapshot.schema.json](schemas/ai-snapshot.schema.json). Schema проверяет форму, семантические проверки ниже — ссылки и отношения. Kotlin serialization не заменяет оба слоя валидации.

Полные синтетические примеры: [program.json](examples/program.json), [ai-snapshot.json](examples/ai-snapshot.json). Это фикстуры обмена, не персональное назначение весов. Выпущенного приложения ещё нет: v1 уточняется до реализации, совместимость с черновиками не обещается.

## Общие правила

- UTF-8, конечные JSON-числа; UI принимает запятую и точку, JSON — точку.
- schema_version — целое 1. Неизвестная версия, неизвестное поле и повторяющиеся ключи JSON отклоняются явно.
- Timestamps — RFC 3339 с offset или Z; date — действительная YYYY-MM-DD без timezone-конвертации.
- ID — непустая стабильная строка. Ключ версии программы — `(program_id, program_version)`.
- Нет вычисленных оценок прогресса/усталости/калорий/безопасности или рекомендаций нагрузки.
- Отсутствие отметки = не сообщено, а не подтверждение отсутствия проблемы.
- Максимум 10 MiB на файл, вложенность до 32 уровней. Проверка вне UI thread; превышение даёт ошибку без частичной записи. Это транспортные, не тренировочные ограничения.

## Программа

Корень: schema, schema_version, program_id, program_version, generated_at, equipment_upserts, workouts. Необязательные athlete_context и coach_notes — текст для хранения/отображения без интерпретации. athlete_context содержит только подтверждённые пользователем цель, опыт, ограничения; пропуски не заполняются догадками.

Оборудование: equipment_id, name, setup_hint (null если неизвестна), необязательные weight_step_kg, available_weights_kg, notes. available_weights_kg — строго возрастающие доступные ступени, при наличии приоритетны для −/+, но не ограничивают ручной ввод факта. Upsert обновляет переданные поля; отсутствие необязательного поля сохраняет старое, null очищает nullable-поле. Локальное фото не затрагивается.

Workout: workout_instance_id, template_id, title, planned_date, blocks; notes необязательна. ID занятия сохраняется между версиями при переносе даты, новый ID обозначает новое занятие. template_id группирует A/B, не задаёт повторения.

Блок: block_id, title, mode, exercises, необязательная notes. straight — ровно одно упражнение; rotation — минимум два. Порядок блоков — порядок массива. Приложение не достраивает разминку или прогрессию.

### Идентичность упражнения

| Поле | Значение |
|---|---|
| exercise_instance_id | Уникальная позиция внутри workout; ключ карточки/черновика/слотов |
| exercise_id | Семантическое упражнение; может повторяться в других блоках |
| title | Понятное название |
| equipment_id | Плановый тренажёр или null |
| setup_hint | Настройка данного упражнения или null |
| load_basis | Способ записи веса, см. ниже |
| side | bilateral / left / right |
| planned_order | Уникальный положительный целый номер в блоке |
| rir_capture | none / last_work_set / all_work_sets |
| planned_sets | Непустой массив конкретных подходов |
| notes | Необязательная инструкция ИИ о технике/паузах |

Односторонняя работа — отдельные экземпляры с side left/right, чтобы не терять различия повторов. MVP записывает силовые подходы с повторениями: timed holds/кардио не кодируются фиктивными reps.

### Значение нагрузки

| load_basis | Что означает weight_kg |
|---|---|
| machine_display | Показание конкретного тренажёра, не оценка усилия |
| total_external | Весь внешний вес, например гриф + диски |
| per_hand | Вес одной гантели, не сумма двух |
| assistance | Помощь/противовес: больше не означает сложнее |
| bodyweight | weight_kg = 0: внешнего веса нет, масса тела не измерена |

В остальных способах 0 допустим. Никаких конвертаций/сравнений способов приложением. Упражнение с собственным весом и отягощением использует total_external с пояснением в названии. ИИ учитывает exercise_id_actual, оборудование, setup_actual, load_basis_actual и side_actual при сравнении.

### План подхода

set_no — последовательные целые 1..N; set_type — warmup/work; target_weight_kg >= 0; reps_min/max — целые >= 1 и min <= max. target_rir — null или 0..4 (4 = 4+); rest_target_sec — неотрицательное целое.

rest_target_sec — плановая пауза **после этого подхода до следующего действия**, не измерение. В rotation ИИ задаёт паузы для каждого элемента пары, при необходимости поясняет в notes. Приложение показывает «Пауза после: …» у плана/последней строки, отдельный таймер — «С записи: …». Готовность по этим числам не вычисляется. ИИ учитывает также интервал до возврата к тому же упражнению.

### Prefill

1. Черновик конкретного слота имеет приоритет и не перезаписывается при возврате/перестановке.
2. Без черновика — target_weight_kg текущего planned set и reps_min.
3. Предыдущий факт переносится только между соседними плановыми слотами с одинаковыми set_type, весом, reps_min/max, target_rir, rest_target_sec, фактическим упражнением/оборудованием, настройкой, load_basis и side. Предыдущий факт должен быть непосредственно предыдущим плановым слотом, не дополнительным подходом.
4. При новой цели, warmup → work или изменённой настройке — текущий план. При замене упражнения/оборудования/способа нагрузки поле веса пустое до ручного ввода; затем для той же замены и неизменной цели можно повторять введённый вес. Приложение не подбирает вес замены.
5. RIR не заполняется из цели или прошлого факта. Отметки боли/техники не копируются.

## Факт тренировки

workout_id, program_id/version, workout_instance_id, template_id, started_at, finished_at, completion_status, equipment_at_start, sets, skipped_sets; notes необязательна. finished_at null только у active. Полные версии программы вложены в snapshot.programs, ссылка однозначна. На старте локально сохраняется immutable план и контекст оборудования; последующий импорт не меняет их. equipment_at_start экспортирует сохранённые при запуске записи каталога для всех плановых equipment_id, включая пропущенные упражнения; без фото. Это обязательный исторический контекст, а не текущий каталог. Если exercise.setup_hint = null, исходная плановая настройка берётся именно отсюда.

completed — все плановые слоты имеют факты, пропусков нет. ended_early — хотя бы один слот не выполнен (включая явный пропуск). active — пользователь ещё не завершил занятие, даже если все подходы записаны. Нулевой подход не создаётся вместо пропуска.

### Set result

| Поле | Значение |
|---|---|
| set_result_id | Стабильный ID исходной попытки записи, retry идемпотентен |
| sequence_no | Уникальный положительный порядковый номер записи в workout, независимо от блока; после удаления возможны пробелы |
| exercise_instance_id | Позиция исходного плана |
| planned_set_no | Номер слота или null для явно добавленного подхода |
| set_type | warmup/work; для планового слота совпадает с планом |
| exercise_id_actual, title_actual | Фактическое упражнение, включая замену |
| equipment_id_actual, equipment_name_actual | Фактическое оборудование, либо оба null |
| setup_actual | Конкретная настройка на этом подходе или null |
| load_basis_actual, side_actual | Фактический способ веса и сторона |
| weight_kg, reps | Конечный вес >= 0, целые повторы >= 0; reps 0 — реальная попытка без полного повтора |
| rir | null или целое 0..4, 4 = 4+ |
| completed_at | Время нажатия записи, не физического окончания подхода |
| clock | boot_id и elapsed_realtime_ms либо null, если недоступно |
| edited_at | null или время коррекции; completed_at/sequence_no не меняются |
| deviations | Уникальные коды пользовательских отметок |
| note | Необязательный комментарий |

Настройка берётся из exercise.setup_hint, затем из каталога на старте. Название/настройка оборудования копируются в факт и не обновляются задним числом. Новая настройка/замена действует на следующие факты этого экземпляра только в текущей тренировке. План не переписывается. Новое оборудование добавляется в каталог с локальным ID и экспортируется.

### RIR и отклонения

rir_capture управляет показом: none — не спрашивать; last_work_set — последний **плановый рабочий** слот; all_work_sets — каждый рабочий. Warmup не требует RIR. null допустим после «Не оценил». В редакторе оценку можно добавить вручную. При раннем завершении last_work_set последняя выполненная строка может остаться без RIR: значение не выдумывается.

deviations: range_shortened, technique_changed, discomfort, setup_changed, equipment_changed, exercise_changed, other. Для боли/техники пояснение необязательно; для настройки и замены нужен сам факт в соответствующих полях, не только флаг. Пустой массив не доказывает отсутствие проблемы.

### Пропуски и коррекции

skipped_sets: `{exercise_instance_id, planned_set_no, recorded_at, reason, note?}`. reason: null, equipment_busy, time_limit, fatigue, discomfort, other. Одна запись — один слот; нельзя одновременно иметь факт и пропуск. Пропуск остатка создаёт записи только для незакрытых слотов, «Вернуть в план» снимает отметки. При досрочном завершении незаписанным слотам не назначается выдуманная причина.

Правка/удаление в истории меняет Room и следующий экспорт; ранее отправленный файл не обновляется. ИИ заменяет прежний результат с тем же workout_id актуальным snapshot, не суммирует копии. Журнал всех правок/tombstones не входит в MVP. Дополнительные подходы не закрывают плановые слоты.

## Время и честность измерения

completed_at фиксируется при первом нажатии **до записи БД**, вместе с ID; retry не сдвигает время. «Сохранено» только после commit. Черновики не являются выполненными подходами и не экспортируются.

Записи 19:17:14 и 19:19:31 дают 137 секунд **между записями**, включая следующий подход, ввод и другие упражнения. Не экспортировать это как actual_rest_sec. ИИ не может восстановить чистый отдых: начало подхода в MVP не собирается.

Для таймера и интервалов в пределах одной загрузки сохраняется elapsedRealtime, включающий сон. boot_id — локальная метка загрузки ОС, стабильная при смерти процесса (системный boot count; если надёжно определить нельзя, clock = null). Разные boot_id не вычитаются. После перезагрузки/при неизвестном clock — max(0, разница wall timestamps), UI показывает «≈». Отрицательный/аномальный интервал ИИ считает неопределённым. sequence_no сохраняет порядок при переводе часов. Background service не нужен. Источник: [Android SystemClock](https://developer.android.com/reference/android/os/SystemClock).

## Импорт и неизменяемость

Одинаковые ID/версия и разобранное содержимое (порядок ключей/пробелы несущественны) → no-op без upsert и смены активной программы. Иное содержимое под тем же ключом → конфликт, импорт целиком отклонён; нужна новая версия. Исторические версии не заменяются.

Новая версия после preview действует только для будущих запусков. Возврат к старой — отдельная явная активация из preview, не эффект повторного импорта. Программа и upserts — одна транзакция. Максимум одна активная тренировка; двойной запуск защищён транзакцией/уникальностью БД.

### Семантические проверки сверх Schema

1. equipment_id уникальны; ссылки существуют локально/в upserts.
2. workout_instance_id уникален в программе; block_id и exercise_instance_id уникальны в workout; planned_order уникален в блоке. exercise_id повторяться может.
3. set_no идут 1..N; reps_min <= reps_max; available_weights_kg возрастают; bodyweight требует вес 0.
4. Ссылки результата разрешаются в неизменной версии программы, template_id совпадает. Фактические equipment_id есть в snapshot каталоге; историческое имя может отличаться от текущего.
5. set_result_id уникальны во всём snapshot; sequence_no уникальны внутри workout. Плановые слоты фактов/пропусков существуют, не дублируются и не пересекаются; set_type совпадает с планом.
6. completion_status согласован с покрытием плана и finished_at; active максимум один. Wall-clock может идти назад, порядок задаёт sequence_no.
7. programs уникальны по ID/версии, workouts по workout_id. active_program и focus_workout_id разрешаются либо null.
8. history_scope правдив: total_stored_workouts = included_workouts + omitted_workouts; included_workouts = длина workouts. Связанные версии программ не отбрасываются при ограничении размера.

## Snapshot и охват

Корень: schema, schema_version, exported_at, app, active_program (ссылка/null), focus_workout_id (ID/null), history_scope, equipment, programs, workouts.

Охват: последние **24 законченные** completed/ended_early по started_at (при равенстве workout_id), плюс активная, плюс выбранная из History, если не вошла. Дедупликация по workout_id. На Finish/Today focus — последняя законченная, до первой — null. Все связанные версии программ и активная программа включены полностью. Каталог может содержать ещё не использованное оборудование.

history_scope: completed_limit = 24, total_stored_workouts, included_workouts, omitted_workouts. При omitted_workouts > 0 ИИ не делает вывод о полной посещаемости по усечённой истории. 12 недель — лишь пример для двух занятий в неделю, не гарантия календарного покрытия.

До первой тренировки экспорт разрешён: workouts = [], остальные доступные данные сохранены. Приложение не подсчитывает мышечный объём. Экспорт читает согласованный snapshot БД; при превышении 10 MiB показывает ошибку, не режет историю молча. В v1 нет автоматического разбиения/сжатия.

Это не полный backup: фото исключены, история ограничена, восстановления базы из snapshot в MVP нет.

## Передача файла

«Отправить JSON» создаёт файл, Android chooser требует выбора получателя: одно действие **в Sportzal**, не автоматическая доставка адресату. application/json; ACTION_SEND, EXTRA_STREAM, content URI FileProvider, временный read grant и ClipData. Provider не экспортируется целиком, доступна только директория exports.

Имя уникально: `sportzal-ai-YYYY-MM-DD-HHmmss-<export-id>.json`. Атомарная запись, следующий экспорт не перезаписывает старый. Не удалять файл при закрытии chooser: получатель может читать позже. Уборка удаляет только экспорты старше 7 дней; ОС может очистить cache раньше. Ошибка/отмена сохраняет Room, повтор создаёт новый файл. Вторичное «Сохранить файл» через ACTION_CREATE_DOCUMENT — когда нет нужной цели отправки.

Системный picker обязателен; «Открыть с помощью» зависит от совместимого intent другого приложения. Проверять содержимое, не только MIME/расширение. Для application/octet-stream или отсутствующего Open with пользователь сохраняет JSON и выбирает его в Sportzal. Snapshot в импорте программы отклоняется с понятным объяснением.

Создание JSON/запись работают офлайн; доставка зависит от клиента/сети. Chooser не доказывает доставку. Источники: [Android sharing](https://developer.android.com/develop/ui/compose/sharing/send), [FileProvider sharing](https://developer.android.com/training/secure-file-sharing).

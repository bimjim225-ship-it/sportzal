# Ревью концепта Sportzal — 6 сентября 2026

Проверены все шесть исходных документов на main `b5752e7`, их взаимная согласованность и полный путь «план → тренировка → файл → ИИ». Это проверка спецификации: Android-приложения ещё нет.

## Вердикт

Концепт подходит одному владельцу: быстрый локальный журнал с внешним анализом ИИ. Главный риск исходной версии — не нехватка аналитики, а потеря или неоднозначность фактов при вводе. Нужны аккуратные контракты, а не встроенный тренер. Интерфейс остаётся «вес → повторы → RIR при запросе → записать»; дополнительные действия доступны только по необходимости.

С тренерской стороны положительны разделение плана/факта, рабочей нагрузки/разминки, наличие RIR, конкретного оборудования, блоков и редких отклонений. Подбор программы по цели и переносимости остаётся снаружи. Само чередование разных мышц не доказывает, что пара удачна; ИИ должен учитывать порядок, доступность оборудования и утомление. Для неизвестного состояния пользователя нельзя подтверждать безопасность конкретной программы.

Выбор простого интерфейса согласуется с акцентом ACSM на регулярности и индивидуализации; отказ и сложная периодизация не являются универсально необходимыми для среднего здорового взрослого. Это общая опора для разделения обязанностей, не назначение данному пользователю. [ACSM, обновление 2026](https://acsm.org/resistance-training-guidelines-update-2026/).

## Что не добавлено

Нет обязательных анкет, графиков, расчёта тоннажа, встроенной прогрессии, оценки боли, выбора замены, Firebase, веб-клиента или фонового секундомера. athlete_context/notes — необязательный текст для внешнего ИИ. Разминка задаётся явно планом. Большой круг допустим форматом, но не объявляется основным или оптимальным режимом.

## Независимое ревью

Второй reviewer проверил документы и примеры. Выявил потерю планового контекста каталога для ещё не выполненных/пропущенных упражнений: исправлено через equipment_at_start. Пример специально обновляет текущую настройку тяги на «Упор 5», сохраняя «Упор 3» на старте и в старом факте.

## Проверка и границы доказательства

Для повторения проверки: открыть терминал VS Code **в корне клона sportzal**, установить зависимости `python -m pip install -r requirements-docs.txt`, затем запустить `python tools/validate_docs.py`. Скрипт читает docs/schemas, docs/examples и Markdown; Android не запускает. Он проверяет Draft 2020-12, полноценные примеры, отрицательные структурные/ссылочные случаи, ссылки, YAML и контраст основных текстовых пар. Это conformance-проверка документации, не замена будущего Kotlin validator или тестов Android.

Результат: 2 схемы, 6 допустимых и 25 отклонённых сценариев; ссылки, YAML и 9 пар текстового контраста — PASS. `git diff --check` — PASS. Статический аудит Frontend Design Premium в strict-режиме — 0 ошибок/предупреждений (см. [JSON](premium-audit.json)). Официальный `npx --yes -p @google/design.md designmd lint DESIGN.md` — 0 ошибок, 11 предупреждений об отсутствии ссылок на токены в конфигурации компонентов. Токены описаны в тексте; runtime theme ещё нет, их привязка проверяется при реализации, не объявляется выполненной.

Ограничения до реализации:

- KPI 3–5 секунд ещё не измерен. Приёмка на телефоне: десять обычных подходов с предзаполненным весом, изменение повторов и RIR; целевая медиана ≤5 секунд без ошибок записи. Исключения/набор комментария измеряются отдельно.
- Compose UI, клавиатура, TalkBack, 320 dp/200%, process death, перезагрузка, атомарность Room и фактическая доставка вложения требуют реализации и проверки на устройстве.
- Android chooser нужно проверить на установленном Telegram/почтовом клиенте: получение JSON **файлом**, скачивание на компьютере, загрузка в чат и обратный импорт новой программы. Открытие chooser не доказывает доставку. [Android sharing](https://developer.android.com/develop/ui/compose/sharing/send).
- Только подходы с повторениями. Кардио/упражнения на время не представлены в v1. Внешний ИИ не должен их кодировать фиктивными повторениями.
- Точное физическое время отдыха, объективная техника и RIR не измеряются; пустая отметка не подтверждает отсутствие проблемы.
- Snapshot — выборка для анализа, не полный backup. Сам по себе не защищает локальную историю при потере телефона.

После исправлений можно переходить к отдельному плану реализации MVP, сохраняя эти ограничения и проводя реальные проверки вместо утверждений по макетам.
